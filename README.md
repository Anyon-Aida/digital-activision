# Digital Activision – Developer Portfolio V2

Digital Activision Portfolio V2 is a bilingual, developer-first engineering portfolio for Kovács Zalán. It uses the Next.js App Router to present verified engineering evidence, typed case studies, an interactive Engineering Lab, and the existing agency offering as a separate Studio experience.

Delivery status: implementation is complete on `rebuild/developer-portfolio-v2`, and the final local gate is green at executable head `5f6aa44`. The automated suites, three-browser release smoke, bundle budget, and three-run-per-locale Lighthouse measurement are recorded in the [final QA report](docs/portfolio-v2/final-qa.md). Vercel Production Branch verification, Preview deployment evidence, and project-owner review are **pending**. No `main` merge or production deployment is implied by this repository state.

## 1. Project overview

The application serves two audiences without mixing their information architecture:

- recruiters, engineering leaders, and collaborators evaluating full-stack work;
- business visitors looking for the Digital Activision Studio offering.

Hungarian and English are first-class locales. The default entry point redirects to Hungarian, while every public application route uses an explicit locale prefix.

Primary routes:

| Route | Purpose |
| --- | --- |
| `/` | Redirects to `/hu` |
| `/hu`, `/en` | Developer-first homepage |
| `/[locale]/work` | Typed case-study index |
| `/[locale]/work/[slug]` | Validated case-study detail |
| `/[locale]/lab` | Engineering Lab and conceptual system demonstrations |
| `/[locale]/studio` | Preserved agency services, process, packages, and experiments |
| `/[locale]/privacy` | Localized privacy information |
| `/api/contact` | First-party, validated contact endpoint |
| `/api/health` | Minimal, uncached health/build response |

Legacy public demo URLs are preserved through explicit permanent redirects. See [the migration guide](docs/portfolio-v2/migration-guide.md) for the complete mapping.

## 2. Product strategy: Developer Portfolio + Studio

The default experience is an engineering portfolio, not an agency sales landing page. Its hierarchy is:

1. engineering positioning and current stack;
2. system-thinking overview;
3. evidence-backed case studies;
4. capabilities linked to evidence;
5. experience and delivery standards;
6. Engineering Lab;
7. Studio hand-off;
8. first-party contact flow.

The Studio route retains the audited agency content and pricing context without allowing it to dominate the developer homepage. Unconfirmed package data remains visibly marked as requiring project-owner confirmation. Legacy experiments are classified as concepts or prototypes and are excluded from indexing.

Content policy:

- do not invent metrics, responsibilities, production status, or technology claims;
- keep private work anonymized;
- mark conceptual diagrams, reconstructed flows, planned work, and unverified details explicitly;
- use “production”, “live”, and “open source” only when the repository evidence supports them.

## 3. Architecture

The application is server-first. React Server Components render navigation, content, metadata, and route shells; Client Components are limited to interaction islands that require browser state.

```text
request
  -> proxy locale / legacy / canonical-path validation
  -> localized App Router layout
  -> typed and validated content registry
  -> Server Component route
  -> optional client interaction island
```

Key boundaries:

- **Routing and locale boundary:** `src/proxy.ts` and `src/i18n/` validate locale-prefixed routes and integrate `next-intl`.
- **Presentation boundary:** route files under `src/app/` compose feature components without owning portfolio facts.
- **Content boundary:** `src/content/` stores bilingual, typed data; case studies and Lab data are validated with Zod.
- **Interaction boundary:** dialogs, mobile navigation, the command palette, filters, architecture explorers, and the contact form are isolated Client Components.
- **Contact boundary:** the browser posts a strict JSON contract only to `/api/contact`; provider credentials and abuse controls stay server-side.
- **SEO boundary:** locale-aware metadata, canonical/alternate links, social images, sitemap, and fail-closed robots behavior are generated by the application.
- **Legacy boundary:** allowlisted static demos remain under `public/projects/`; unknown legacy-like routes fail closed.

The health endpoint is deliberately not a dependency-readiness probe. It exposes only a safe status, validated short commit identifier or `unknown`, optional build timestamp, and request ID.

### Route and cache policy

| Route family | Rendering/cache class | Policy |
| --- | --- | --- |
| `/[locale]`, `/work`, case studies, Lab, Studio, privacy | Dynamic server output | Server-rendered on demand from validated repository content; there is no application data cache. Case-study params fail closed. |
| `/robots.txt`, `/sitemap.xml` | Static metadata output | Generated for the build environment; Preview indexing fails closed and only ready public work is listed. |
| Homepage and Work social-image routes | Deterministic Edge route | Generated on demand from validated content; no application-level revalidation interval is configured. Platform response caching remains Vercel-managed. |
| Case-study social-image routes | Static build output | Generated for every validated HU/EN slug through `generateStaticParams`. |
| `/api/contact` | Dynamic and uncached | `force-dynamic`; every response sends `Cache-Control: no-store, max-age=0`. External limiter and Turnstile calls also use `no-store`. |
| `/api/health` | Dynamic and uncached | `force-dynamic`; every request returns fresh safe build/request metadata with `Cache-Control: no-store, max-age=0`. |
| Locale/canonical/legacy redirects | Request boundary or dynamic redirect route | No repository data fetch or application response cache; the explicit permanent redirect response is safe for clients/CDNs to retain. |
| `/projects/*` preserved demos and other `public/` assets | Static asset | Served as deployment assets under Vercel’s static/CDN policy. Changes require a new deployment. |

No application route currently uses time-based ISR. Introducing `revalidate` or a data cache requires an explicit freshness, invalidation, and failure-mode review.

## 6. Local setup

Requirements:

- Node.js `20.19.x` (`.node-version` and `.nvmrc`);
- npm `10.8.2`, or a lockfile-compatible npm release;
- Chromium, Firefox, and WebKit installed by Playwright for the committed automated and release-smoke suites.

Install and start:

```powershell
git rev-parse --abbrev-ref HEAD
npm ci
Copy-Item .env.example .env.local
npx playwright install chromium firefox webkit
npm run dev
```

The local URL is `http://localhost:3000`. `/` redirects to `/hu`; English starts at `/en`.

To exercise the production server locally:

```powershell
npm run build
npm run start
```

Keep `CONTACT_FORM_ENABLED=false` unless intentionally testing a complete local mail configuration. Never reuse Production secrets or recipients for routine local testing.

The committed Playwright configuration defines Chromium, Firefox, and WebKit. The broad E2E, axe, and visual suites remain Chromium-scoped; `test:cross-browser` runs the focused release smoke in all three engines.

Copy `.env.example` to `.env.local`. Committed files contain names and safe defaults only; secrets belong in local secret storage or the correctly scoped Vercel environment.

| `VERCEL_PROJECT_PRODUCTION_URL` | Vercel system | Stable fallback canonical production origin |

Do not copy Vercel system variables into committed env files.

### Contact feature gates and origins

| Variable | Requirement |
| --- | --- |
| `CONTACT_FORM_ENABLED` | Must be exactly `true` before delivery can run |
| `CONTACT_PREVIEW_ENABLED` | Additional explicit Preview-only enable switch |
| `CONTACT_ALLOWED_ORIGINS` | Comma-separated exact origins; no paths or wildcards |
| `CONTACT_MIN_FILL_MS` | Optional minimum human-fill duration |
| `CONTACT_MAX_FORM_AGE_MS` | Optional maximum accepted form age |

### SMTP and environment-specific recipients

| Variable | Requirement |
| --- | --- |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS` | Required whenever delivery is enabled |
| `CONTACT_TO`, `CONTACT_FROM` | Non-Preview recipient and sender |
| `CONTACT_PREVIEW_TO`, `CONTACT_PREVIEW_FROM` | Required separate Preview recipient and sender |

Preview never falls back to `CONTACT_TO` or `CONTACT_FROM`.

### Rate limiting and Turnstile

| Variable | Requirement |
| --- | --- |
| `CONTACT_RATE_LIMIT_ENDPOINT` | HTTPS external limiter endpoint; required in Preview/Production |
| `CONTACT_RATE_LIMIT_TOKEN` | Bearer token for the external limiter |
| `CONTACT_RATE_LIMIT_KEY_SECRET` | HMAC secret; at least 32 characters in Preview/Production |
| `CONTACT_RATE_LIMIT_MAX` | Optional request limit |
| `CONTACT_RATE_LIMIT_WINDOW_MS` | Optional window in milliseconds |
| `NEXT_PUBLIC_TURNSTILE_SITE_KEY` | Browser-visible Cloudflare Turnstile site key |
| `CONTACT_TURNSTILE_SECRET_KEY` | Server-only Turnstile secret |

The external limiter receives a bearer-authenticated JSON `POST`:

```json
{
  "key": "opaque-hashed-client-key",
  "limit": 5,
  "windowSeconds": 600,
  "requestId": "request-id"
}
```

It must return a strict JSON object:

```json
{
  "allowed": true,
  "retryAfterSeconds": 0,
  "remaining": 4
}
```

`remaining` is optional. Non-success, malformed, or timed-out limiter responses fail the contact request closed.

Environment behavior:

- **Local development:** contact is disabled by default; an enabled development form uses the bounded in-memory limiter.
- **Preview:** contact remains disabled unless both feature gates are enabled and separate Preview SMTP, external limiter, and Turnstile configuration is valid.
- **Production:** delivery requires the complete SMTP, external limiter, origin, and Turnstile contract.

Actual Preview variable presence and isolation are **pending manual verification**. Do not print values in CI logs, PRs, screenshots, or documentation.

- **E2E:** critical localized routes, legacy redirects, case studies, Studio, Lab, command palette, contact states, SEO/privacy, health and security headers.

## 11. Localization

Supported locales are `hu` and `en`; Hungarian is the default. `localePrefix: "always"` keeps public application routes explicit and `localeDetection` is disabled for deterministic routing.

`next-intl` provides request configuration, localized navigation helpers, and shared messages. Domain content uses typed bilingual fields so that case-study validation can require HU/EN parity at build/test time.

Routing rules:

- use helpers from `src/i18n/navigation.ts` for localized application navigation;
- validate route params with the supported locale list;
- preserve query strings and hashes when switching locale where the interaction requires it;
- keep canonical and `hreflang` metadata aligned;
- unknown locale-shaped routes and unknown case-study slugs must fail closed.

Never introduce a second parallel global dictionary system. New locale support requires routing, content, metadata, sitemap, testing, and migration updates together.

## 13. Security notes

- The contact endpoint accepts a strict, size-limited JSON payload and uses server-side Zod validation.
- Contact delivery is fail-closed when feature gates or environment configuration are incomplete.
- Preview uses separate sender/recipient variables and never falls back to Production contact addresses.
- Production/Preview require a distributed HTTPS rate limiter and Turnstile; the in-memory limiter is development-only.
- Client identifiers are HMAC-derived before rate limiting; raw form bodies and credentials must not be logged.
- User-facing errors are generic and include safe request IDs; structured server logs minimize PII.
- The global response policy includes CSP, referrer policy, permissions policy, MIME sniffing protection, and frame denial.
- HSTS is emitted only when `VERCEL_ENV=production`.
- Preview indexing fails closed; legacy experiments additionally receive `X-Robots-Tag: noindex, nofollow, noarchive`.
- `.env.local`, Vercel values, tokens, passwords, Turnstile secrets, and real contact payloads must never be committed.

External monitoring such as Sentry is not configured by this rebuild and requires separate project-owner approval.

## 14. Accessibility and performance targets

Implemented accessibility foundations include semantic landmarks, skip navigation, localized document language, focus-managed dialogs/sheets, keyboard-operable navigation and architecture controls, visible form labels/errors, live status regions, and reduced-motion handling.

Release targets:

- no serious or critical axe violations on covered critical states;
- complete keyboard-only access and reliable focus return;
- no horizontal overflow at 320 px;
- meaningful fallback text for visual system diagrams;
- localized accessible names and validation states;
- no known critical console or page errors.

Automated coverage does not replace the remaining project-owner/manual release matrix: NVDA or VoiceOver smoke, 200% browser zoom, representative iPhone Safari and Android Chrome, full keyboard-only route review, slow-network behavior, and final Preview copy/console inspection. These are tracked explicitly in the final QA and deployment checklist.

Performance/SEO targets and current evidence:

- Next.js image optimization is restored; the global `images.unoptimized` override is removed and commit `c68fcc9` adds explicit optimized public case-study media coverage (targeted suite 15/15);
- reserve priority loading for genuinely critical assets;
- keep client islands and route bundles reviewable; the homepage currently reports 42.1 KiB gzip against its 165 KiB budget;
- target approximately 90 or better Lighthouse mobile performance while prioritizing Core Web Vitals and real UX;
- no critical Accessibility, Best Practices, or SEO failures;
- correct locale metadata, canonical/alternate links, sitemap, and Preview noindex behavior.

The three-run mobile Lighthouse medians are Performance 96, Accessibility 100, Best Practices 100 for both locales. The local SEO score is 58 because the measurement intentionally ran without `VERCEL_ENV`, so fail-closed noindex and the production canonical origin fail Lighthouse’s crawlability/canonical audits; dedicated metadata/robots E2E coverage is green. Median LCP is 2571.074 ms for HU and 2566.598 ms for EN, leaving a 66–71 ms risk above the 2.5 s production target. Preview/Production verification and the remaining manual accessibility/performance matrix are **pending**.
